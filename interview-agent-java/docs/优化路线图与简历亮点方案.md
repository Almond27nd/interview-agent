## 现状基线（⚠️ 已过时，仅保留作为"优化前"的对照；最新现状见文末「现状基线更新」）

```
StateGraph（7 节点，纯线性 + 3 处二元条件边）
START → jd_analysis → resume_match → question_plan → interview
                                                          │
                                     (未作答即终止)──────┴── END
                                                          │
                                   weak_review → evaluation → review_plan → END
```

- 7 个 Agent 里 **6 个是"单轮 LLM 调用"**（JDAnalyzer / ResumeMatcher / QuestionPlanner ×2 /
  Interviewer / Evaluator），只有 `ReviewPlanner` 用了 `com.alibaba.cloud.ai.graph.agent.ReactAgent`，
  挂了一个 `GitHubTool`（`FunctionToolCallback`），让模型自主判断"要不要搜、搜什么关键词"。
- Graph 的 state 是**空的**（只有一个占位 key），业务上下文全放在 `Orchestrator.Ctx` 闭包里，
  这是为了绕开 graph 对 state 做 Jackson 深拷贝快照、又要塞阻塞回调/业务大对象的矛盾——
  这个设计本身已经是一个亮点（"该用 graph 的地方用 graph 编排流程/条件分支，
  不该硬塞进 state 序列化的东西不硬塞"），但代价是**graph 目前只承担了"调度骨架"的角色，
  没有用上 checkpoint / 并行 fan-out / 子图 这些更能体现"多 Agent 编排"技术深度的能力**。

下面的优化，就是在不推翻现有架构的前提下，把"骨架"升级为"真正体现多 Agent 编排价值"的设计。

## Part A：Graph 多 Agent 编排层的优化点

### A1. 面试断线重连 —— 引入 Checkpoint / 持久化状态（★ 最值得做，工程含金量最高）

**现状问题**：`interview()` 节点内部用 `c.cb.getUserAnswer()` **阻塞当前线程**等用户答题。
这意味着一场面试的"进度"完全绑定在一条 JVM 线程的调用栈上——服务重启、线程被杀、
容器重新调度，整场面试直接丢失，用户从第 1 题重新开始。

**要做什么**：
1. 给 `InterviewState`（当前已问到第几题、每题得分、连对/连错计数、候选人画像）设计一个
   可序列化的 checkpoint 结构，每答完一题就落一次盘（Redis 或 MySQL，写一条即可，成本很低）。
2. `Orchestrator.runInterview` 增加一个"恢复模式"入口：传入 `sessionId` 时，先尝试从
   checkpoint 加载 `InterviewState`，`StageScheduler` 从对应题号续跑，而不是从 `question_plan`
   节点重新执行一遍。
3. 前端 WebSocket 断开重连时，后端根据 `sessionId` 判断"是否有未完成的 checkpoint"，
   有则直接进入 `interview` 阶段续答，不重新走 jd_analysis / resume_match / question_plan。

**为什么这么设计**：面试是一个可能持续 10~30 分钟的长会话，中途网络抖动/浏览器刷新
是大概率事件；现在的"全内存 + 阻塞线程"模型在演示环境下没问题，但暴露了"单点故障
会导致整个长流程从头开始"的架构短板——这恰恰是"图编排"框架本该解决的问题
（LangGraph/Spring AI Alibaba Graph 都提供了 Checkpointer/Saver 机制）。

**相比 naive 做法的优势**：naive 做法是"整场面试放 Redis Session，断了就重来"，
或者干脆不处理断线；这里是**把 Graph 的状态管理能力（state snapshot）和面试业务的
关键进度字段结合**，只对必要的字段做增量持久化（不是整个 Ctx 序列化，避免踩到
"Ctx 里有阻塞回调不能序列化"的坑），用最小代价换来断线可恢复。

**面试话术**：*"面试流程本身是一个跑很久的有状态图，我给它加了一层轻量 checkpoint，
每答完一题落一次盘，服务重启或用户断线重连后可以从中断的题号续答，而不用从头重来——
这是我在使用 Graph 编排框架时特意补的一课，因为默认的顺序编排/单机内存态在生产环境
下是不够的。"*

### A2. 把"隐藏在方法体里的分支"提升为图的显式条件边

**现状问题**：`weakReview` 是否要巩固低分题，`interview` 里是否要追问，这些分支逻辑
现在都是 `if` 语句藏在节点方法体内部，从图结构上完全看不出来——`Orchestrator.runInterview`
里画出来的图，和实际运行时的分支走向是不一致的（图上看永远是
`interview → weak_review → evaluation`，但 weak_review 内部可能什么都不做）。

**要做什么**：把"本场是否存在低分题"提升为一条 `addConditionalEdges`，
`interview → (有低分题) weak_review → evaluation`；`interview → (无低分题) evaluation`（跳过节点）。

**为什么这么设计**：图的价值之一就是"看图就能理解系统会怎么走"，条件判断藏得越深，
图的自文档能力就越弱，后续接可视化/追踪工具（见 Part D）时，"节点是否被跳过"这个
信息也更容易在 trace 里体现（跳过的节点根本不产生 span，一眼看出这场面试没有低分题）。

**面试话术**：*"我把原来隐藏在方法体里的业务分支，尽量上升成图的条件边，让图结构和
真实执行路径保持一致，这样图既是编排骨架，也是天然的可观测文档。"*

### A3. 并行化图中互不依赖的步骤（Fan-out / Fan-in）

**现状问题**：`questionPlan` 节点内部，"读取跨会话历史薄弱点"（`longTermMem.getWeakPoints`）
和"读取同岗位历史面试趋势"（`mysqlStore.getRecentInterviewRecords`）是两次**互不依赖**
的存储查询，代码里却写成了顺序两步；`weakReview` 节点里对 N 道低分题逐一调用
`retrieveReferenceAnswer`（RAG 检索）生成巩固内容，同样是可以并行的独立 LLM/检索调用，
现在也是 for 循环顺序跑。

**要做什么**：
- 两次历史查询用 `CompletableFuture.allOf` 并发发起，都返回后再继续 Phase 1 规划。
- `weakReview` 里对多道低分题的巩固内容生成改成并行流（`parallelStream` 或
  `CompletableFuture` 组合），控制并发度避免打爆 LLM 限流。

**为什么这么设计**：面试全流程里唯一的性能敏感点就是"多次串行 LLM/IO 调用叠加的等待时间"，
这两处是少数"确定无依赖关系"的环节，并行化零风险、纯收益。

**相比 naive 做法的优势**：naive 做法是"哪里慢就加缓存/换更快的模型"，这里是先做
**依赖分析**，把本来就没有先后关系的调用从"图省事写成顺序代码"还原成"并行执行"，
是更精细的工程优化姿势。

### A4. Evaluator-Critic 双 Agent 交叉校验（用多 Agent 协作换"评分可信度"）

> ## ⬜ 未开始，但**同一模式已在出题环节落地**（见 Part B 的「新增条目 B4」）
>
> 如果要做这一项，**可直接复用 B4 已经踩过的经验**，不用重新设计：
>
> | B4 已验证的做法 | 迁移到评分场景 |
> |---|---|
> | `QuestionDefect` 统一缺陷结构 + `direction_index` 作 join key | 换成 `questionId` 或题号作 join key，结构可照抄 |
> | 先跑纯 Java 规则预检，再跑语义 Critic | 评分场景同样有机械可判定项：`keyPointsHit` 为空却给了高分、各维度分与总分算术不一致、分数超出 0~100 —— 这些用代码判即可，不必花 token |
> | Critic 无工具、只判不改，改动权归 Generator | 同理：Critic 只标记"该题分数与依据不自洽"，是否调分交还 `Evaluator` |
> | `MAX_REVIEW_ROUNDS = 2` 截断 + fail-open | 直接沿用。评分环节尤其要 fail-open —— Critic 挂了不能让报告生成失败 |
> | Critic instruction 里的"审核纪律"段落（含"全部 pass 是正常结果"的显式许可） | 直接复用文案思路，抑制 LLM 做 Critic 时的过度严苛 |
> | Critic 用单轮 `chatModel.call` 而非 `ReactAgent`（无工具就不需要 ReAct 循环） | 同样适用 |
>
> **⚠️ 但要先想清楚一个差异**：出题环节的缺陷（重复、难度不符）是**可客观验证**的，
> 而"评分准不准"本身缺少 ground truth，Critic 的判断质量难以度量。所以这一项的收益
> 不如 B4 明确——建议先接入 Part D 的可观测性，有了 Trace 和数据再评估是否值得做。

**现状问题**：`Evaluator` 是单个 LLM 一次性对整场面试打分出报告，打分本身没有任何
"复核"机制——LLM 打分存在方差，同一份回答不同次调用可能给出不同分数，用户体验上
"AI 打的分到底准不准"是天然的信任痛点。

**要做什么**：在 `evaluation` 节点后面加一个轻量 Critic 节点：拿 `Evaluator` 产出的
`EvaluationReport`（各维度分 + 依据），让第二个（可以是同模型不同 prompt，也可以是
更便宜的小模型）Agent 只做"复核"——检查"分数与给出的依据是否自相矛盾"、
"是否有 keyPointsHit/Missed 与最终分数明显不符的题"，发现问题就微调分数或标记
"建议人工复核"，而不是重新打一遍分（成本可控）。

**为什么这么设计**：这是经典的 Generator-Critic / Reflection 模式在评分场景的落地——
比"多 Agent 投票平均分"更便宜（Critic 只读依据不重新推理），比"完全不做校验"更可信。

**面试话术**：*"评估报告是面试官视角对候选人最终的定性，我加了一个 Critic Agent
专门复核打分依据和分数是否自洽，用小成本的二次校验换取评分可信度，而不是简单地
多跑几次投票平均——那样成本会翻倍。"*

## Part B：ReactAgent（`ReviewPlanner`）方向的深度改造 ★★★ 重点

全项目目前只有 `ReviewPlanner` 用了真正的 Tool-calling ReAct 循环（挂 1 个 `GitHubTool`），
这是最适合"深挖出更多技术亮点"的单点——不需要动 Graph 结构，只在这一个 Agent 内部
持续加深，天花板很高。以下按"从易到难、从工具到能力"排序：

### B1. 把现有"过程式 RAG pipeline"改造成 ReactAgent 自主 Tool-use（技术含量最高的一项）

> ## ✅ 已完成 —— 且做到了原计划之外的两层
>
> **落地记录**：`B1升级-Router模式与WebSearchTool.md`、`迭代交接文档.md` 第 14.1 节
>
> **实际落地与原计划的差异**（这几点是原计划没想到、落地时才做的决策）：
>
> | 原计划 | 实际做法 | 原因 |
> |---|---|---|
> | 把 Milvus / BM25 / Reranker **分别**封装成三个 Tool，让模型自己决定"要不要重排" | 封装成**一个** `QuestionBankTool.asQuestionAssemblyTool()`，内部固定走"双路召回 + 去重 + Rerank" | 把"要不要重排"这种纯技术细节交给模型判断毫无价值，只会增加它出错的机会。模型该决策的是**业务层面**的"查什么词、信不信结果、要不要换词重试"，不是检索管道的内部实现 |
> | 每个方向 new 一个 ReactAgent | 按 difficulty 分 3 组，**每档复用一个 agent 会话** | agent 实例数量恒定为 3，不随方向数量（未来跨专业可能扩到几十个）线性增长；一次会话内对组内每个方向依次调工具，靠 `direction_index` 显式回填 |
> | — | **额外做了 Router 升级**：新增 `search_web`（博查AI搜索）作为第二个异构检索源 | 原计划只有题库一个来源，按 Agentic RAG 综述的分类只算 Corrective 子类型，够不上 Router。加了网络源才有真正的"路由"语义，同时解决"冷门新技术点题库查不到、模型知识过时会编造"的真实痛点 |
>
> **落地时踩到的关键约束**（后续维护务必遵守）：发给模型的工具能力描述必须与实际绑定的
> `tools` 列表严格一致——指令拼接和工具列表构建用**同一个** `hasWebSearch` 布尔变量，
> 否则会出现"指令里提到了 `search_web` 但工具列表没挂"，模型调用不存在的工具而报错。

**现状问题**：`Orchestrator.questionPlan` 里，"要不要去 Milvus/BM25 检索题库、检索几次、
命中了用原题、没命中交给 LLM 出题"这整套逻辑，是 **Java 手写的过程式代码**（30+ 行 for
循环 + if/else），本质上是一个"人工实现的 ReAct 循环"：LLM 规划方向 → 代码决定检索 →
代码判断命中 → 代码决定要不要交给 LLM 兜底出题。

**要做什么**：把 `MilvusStore.retrieveByUser` / `BM25Manager.retrieve` / `Reranker.rerank`
分别封装成 `ToolCallback`（参考 `GitHubTool.asToolCallback()` 的写法），让 `QuestionPlanner`
Phase 2（组装题目）改造成一个 `ReactAgent`：模型自己决定"这个方向要不要检索题库、
用什么 query、检索结果要不要重排、命中度不够时是否换个 query 再试一次、最终是自己出题
还是用检索到的原题"。

**为什么这么设计**：现在的检索逻辑是"一次检索、不满意就放弃、直接兜底 LLM 出题"，
是很死板的单次尝试；交给 ReactAgent 后，模型可以在没检索到满意结果时**自主重试**
（换个更精准的关键词再检索一次），这是"Agentic RAG"相对"传统 RAG pipeline"的
核心优势——检索策略从"写死的一次性调用"变成"模型可以迭代优化的多步决策"。

**相比 naive 做法的优势**：naive 做法是"if 检索到 then 用，else LLM 出题"，
这里是把检索"升级"为模型可以自主判断、重试、组合使用的能力，是 RAG 系统从
"检索增强生成"到"检索增强 Agent"的典型演进路径，也是目前大厂 Agent 团队
最常拿来说的技术方向之一（Agentic RAG / Self-RAG）。

**面试话术**：*"最初的题库检索是我手写的过程式 pipeline：检索、判断命中、不命中
兜底。后来我把 Milvus/BM25/Rerank 都封装成 Tool，让出题 Agent 用 ReAct 循环自主
决定检索策略——比如第一次检索关键词太泛没命中，模型会自己换个更精确的关键词
再试一次，而不是直接放弃转 LLM 出题，这样题库的命中率和出题质量都能提升。"*

### B2. 给 ReactAgent 加"自我验收 + 有限重试"的反思循环

> ## ✅ 已完成（`ReviewPlanner`）
>
> **落地位置**：`ReviewPlanner.generateWithReactAgent`，常量 `MAX_REFLECT_ROUNDS = 2`
>
> 实现与原计划一致：`findUncoveredHighPriorityAreas` 用纯规则代码（`isTopicCovered` 模糊匹配）
> 检查 `weakAreas` 里 `priority=high` 的项是否都能在 `studyPlan` 里找到对应条目，缺失时把
> `buildMissingAreaObservation` 生成的缺口描述作为新 `UserMessage` 追加进 `history`，
> 复用同一个 agent 实例重新调用，最多 2 轮。
>
> **⭐ 这套"规则自检 → 缺口回喂模型"的模式后来被推广了**：B4 的
> `QuestionRuleChecker` 就是把它抽成一个可独立单元测试的通用组件，用在出题环节的
> 两个 Agent 之间做零 token 预检。**同一个方法论在两处落地**，面试时可以作为
> "系统性方法"而不是孤立小功能来讲。

**现状问题**：`ReviewPlanner.generateWithReactAgent` 目前是"调一次 Agent、拿到结果就用"，
即便模型漏掉了某个高优先级薄弱点没安排学习任务，也不会被发现——`AgentUtils.callWithRetry`
的重试只覆盖"JSON 解析失败"这种技术性失败，不覆盖"内容质量不达标"。

**要做什么**：生成复习计划后加一次**自校验**：用代码（不用再调 LLM，纯规则）比对
`report.weakAreas` 里 priority=high 的项，是否都能在 `plan.studyPlan` 里找到对应的
`topic`（模糊匹配）。缺失时，把"缺失的薄弱点列表"作为追加 observation 塞回 ReactAgent
的对话历史，要求它补充，最多补 1~2 轮——这才是 ReAct 论文里"Reason-Act-Observe"
循环该有的样子（现在只做了一步 Act，没有利用 Observe 去驱动下一步 Reason）。

**为什么这么设计**：当前实现里"React"更多是"给了工具，模型决定调不调"，
还没用上"根据执行结果反思、决定下一步"这层——这一项正好补上这个技术深度，
而且成本可控（规则校验不花 token，只有真的漏了才触发第二轮模型调用）。

**面试话术**：*"我给复习计划生成加了一层自校验：用规则代码比对报告里的高优先级
薄弱点是否都被计划覆盖，漏了就把缺口作为新的 observation 塞回给 Agent 让它补充，
最多两轮——这样能保证不会花更多 token 的前提下，把 ReAct 的'观察-反思'环节真正用起来，
而不是只用了'工具调用'这一半能力。"*

**现状问题**：`GitHubTool.searchRepositories` 失败直接返回 `null`（无重试、无限流保护、
无缓存），高频关键词（比如"Redis"、"Spring Boot"）每次都重新打 GitHub API，
容易撞到 GitHub 未认证/低配额的限流。

**要做什么**：
- 给 `asToolCallback()` 包一层短期本地缓存（相同 query 5~10 分钟内直接返回缓存结果），
  用 `Caffeine` 或简单的 `ConcurrentHashMap + TTL` 即可，不需要引入新中间件。
- 给搜索结果加质量过滤：排除 fork 仓库（`item.get("fork").asBoolean()`）、
  按最近更新时间过滤掉长期不维护的项目，避免推荐"star 高但已经三年没更新"的死项目。
- 工具调用失败/超时时返回一句明确的"工具当前不可用"文案给模型，而不是 `null`
  （现在传空字符串给模型走的是"降级为已知资源"分支，但模型无法区分"没搜到"
  和"工具挂了"这两种情况，无法针对性调整策略）。

**面试话术**：*"GitHub 工具本身没做限流保护，我加了一层短期缓存，同一个技术关键词
短时间内不重复打 API，也过滤掉了 fork 仓库和长期不维护的项目，避免给候选人推荐
'star 数好看但早就没人维护'的资源。"*

### 【新增条目】B4·Multi-Agent 出题-审题回环（原文档未列，已完成）

> ## ✅ 已完成
>
> **落地记录**：`B4升级-MultiAgent出题审题回环.md`、`迭代交接文档.md` 第 14.2 / 14.3 节
>
> 这是 B1 之后的自然延伸，也是把 **A4（Evaluator-Critic 交叉校验）的 Generator-Critic 模式
> 在出题环节的一次落地**——原路线图把这个模式规划在评分环节，实际先在出题环节做了，
> 因为那里的收益更明确（评分的"对不对"难以客观验证，而出题的"重复/难度不符"是可验证的）。

**要解决的问题**：B1 之后仍是 Single-Agent，**出题者同时充当自己的质检员**。除了 LLM 自评的
确认偏差，更硬的问题是有几类缺陷它**结构上就发现不了**：

- **跨方向重复**：题库检索是逐方向独立进行的，"MySQL索引优化"和"MySQL B+树"这类邻近方向
  很容易命中实质相同的原题，但出题 agent 的注意力一直在"逐个查库"，不会回头做全局比对；
- **难度名不副实**：题库原题的 `difficulty` 是题库自己标的，照搬进来可能一个 `hard` 方向拿到
  一道只考 API 用法的题，直接破坏 `StageScheduler` 依赖的难度梯度；
- **事实性风险**：`source=web` 依据网页摘要（可能过时），`source=llm` 可能幻觉，自己校验自己
  天然不可靠。

**做了什么**：把 `assembleBasicQuestionsWithAgent` 内部升级为一张带条件回环的 `StateGraph`：

```
START → assemble ──→ review ──[无打回 或 轮次耗尽]──→ finalize → END
           ↑            │
           └────────────┘  [有打回 且 round < 2]
```

三层职责，边界互不重叠（**其中只有两个是 Agent**）：

| 参与者 | 是 Agent | 职责 |
|---|---|---|
| Agent① `question_assembler_group` | ✅ `ReactAgent` + 题库/网络工具 | 检索、选源、出题、按理由重出 |
| `QuestionRuleChecker` | ❌ 纯 Java 静态工具类 | 机械可判定的硬错误（零 token、零误判） |
| Agent② `QuestionReviewer` | ✅ 单轮 `chatModel.call`、无工具 | 语义批判（考点/难度/递进/事实/语义重复） |

**⚠️ 一个被否决的方案**（后续维护者请勿"改回去"）：先评估过更教科书的
**Retriever + Generator** 拆法（即 `B1升级` 文档第 9 节自己埋的"下一步"建议），**否决了**——
题库命中时要求原题照搬，Generator 就近乎透传，两个 agent 职责重叠在"出题"上，说不清第二个
agent 的价值。而"生成 vs 批判"是天然对立的立场，职责零重叠且天然有回环。

**几个关键设计决策**：

1. **为什么插一层纯 Java 规则预检**：机械可判定的错误（难度不一致、字段缺失、文本近重复）
   用代码判又快又零误判，没必要花模型的钱；Critic 得以专注在真正需要理解语义的维度。
   这套模式复用自 B2 的反思循环，这次抽成了可独立单测的组件。
2. **重复阈值 0.6 刻意保守**：实测同义换序（"索引失效的场景有哪些" vs "哪些场景会导致索引
   失效"）相似度只有约 0.5，规则层**故意不报**。调低阈值能抓住它，但会误伤考点相邻但确实
   不同的题目，而**误判代价（合格题白白重出）比漏判更高**。这个边界已固化成显式测试，
   **后续勿轻易调低**。
3. **协作走 Blackboard 而非 agent 间对话**：出题是确定性生成任务，需要以 `direction_index`
   作 join key 的结构化 `QuestionDefect`；自然语言消息无法精确定位"第三道题"是哪一道。
4. **刻意没用框架的 Supervisor 父子 agent 机制**（`AgentTool$AgentToolExecutor` 把 agent
   包装成 tool）：那样"调不调审核"就由出题 agent 自己决定了，正好绕开要解决的确认偏差；
   轮次上限和结论解析也不可控。**原则是：审核的"是否发生、发生几次、结论怎么解析"
   收归代码硬保证，只把"检索什么、怎么出题、判不判合格"交给模型。**
5. **权限边界**：检索权只归出题者，判断权只归审题者。Critic 发现事实存疑时只**标记**
   "需要查证什么"，真正的查证动作交还给带工具的出题 Agent。
6. **两个 Agent 生命周期刻意不对称**：出题 agent 复用实例、累积历史（必须记得上一轮写了
   什么，否则重出时只能瞎猜）；审题 agent 每轮新建、不带历史（避免**锚定效应**——
   "我上轮说有问题，这轮不好意思说没问题"）。
7. **全程 fail-open**：审题是**质量增强**不是**准入门槛**，Critic 挂掉或轮次耗尽一律接受
   当前草稿。绝不能因为 Critic 挂了就让面试没题可问。

**⚠️ 引入回环后新出现的风险点**：`source` 字段的诚实性。重出时若模型改编了题干却仍标着
题库 ID，`Orchestrator.buildWeakReviewContent` 依据 source 回题库取的参考答案就和题目对不上了。
已在重出指令里做强约束，验证清单见 `迭代交接文档.md` 第 14.6 节第 6 条。

**一个值得讲的实现修正**：Critic 初版用了 `ReactAgent` + 空工具列表，后来改成单轮
`chatModel.call`。它没有工具就不存在 thought→act→observe 循环，套一层等于每轮白建一张
`StateGraph`、白绕一层 graph runner、多一层异常包装，还会误导读者以为需要工具能力。
**但它依然是独立 Agent 角色——"是不是 Agent"取决于决策权和角色定位，不取决于用了框架里
哪个类。** 反过来也解释了为什么出题 Agent 必须是 `ReactAgent`。

**面试话术**：*"出题环节我从单 agent 拆成了出题 + 审题两个 agent，用 StateGraph 建了一张带
条件回环的小图。选这个拆法而不是 Retriever/Generator，是因为后者在题库命中时 Generator
近乎透传、职责重叠；而生成和批判是天然对立的角色。协作走 Blackboard 而不是 agent 对话——
出题是确定性任务，需要以 direction_index 作 join key 的结构化 verdict。工程上做了三件事：
一是在两个 agent 之间插一层纯规则预检，机械可判定的错误不花模型的钱；二是只回炉被打回的
方向、复用对话历史，让打回理由能驱动出题 agent 重新检索而不只是重写文本；三是 fail-open，
因为审题是质量增强而不是准入门槛。另外框架其实支持把 agent 包装成 tool 做 Supervisor 父子
结构，我刻意没用——那样调不调审核就变成出题 agent 自己决定了，正好绕开我要解决的确认偏差。"*

## Part D：工程可观测性——Token 统计 + 大模型调用 Trace

**结论先给：不需要自己造轮子。** Spring AI 生态已经原生支持基于
`Micrometer Observation` 的可观测性，本项目要做的只是"接上现成能力"，而这件事
本身就是一个可以写进简历的工程亮点——"知道该用什么现成工具，而不是重复发明轮子"
本身就是能力的体现。

### D1. 现成能力盘点

| 能力 | 提供方 | 说明 |
|---|---|---|
| ChatModel 调用自动埋点 | Spring AI（`ChatClient`/`ChatModel` 内置 Observation） | 每次 `chatModel.call(...)` 自动产生一个 Observation，包含模型名、耗时等，配置好 tracing 依赖后零代码接入 |
| Token 用量指标 | Spring AI Observation 的 `gen_ai.usage.*` 属性 | `input_tokens` / `output_tokens` 会作为 span 属性/tag 暴露，可直接被 Micrometer 转成 Counter 指标 |
| 全链路 Trace 导出 | Micrometer Tracing + OpenTelemetry（OTLP exporter） | 只需引入 `micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp` 依赖 + 配置 exporter endpoint，不用手写埋点代码 |
| 可视化后端（自建） | Langfuse（开源，专做 LLM 可观测） / Grafana Tempo / Jaeger / Zipkin | 都兼容标准 OTLP 协议，Langfuse 尤其适合看 Prompt/Response 回放、按 Agent 维度看 Token 成本 |
| 可视化后端（云上现成） | 阿里云 ARMS「AI 可观测」 | 面向 LLM 应用的探针方案（LoongSuite），可直接对接 Spring AI / LangChain 应用，控制台里看多 Agent 调用链、每次调用的 Token 消耗、耗时，不需要自己搭 Grafana |
| Token 用量与费用统计（模型侧） | 阿里云百炼（DashScope）控制台 | 只要用的是百炼/DashScope 模型，控制台自带"用量统计"和"调用日志"，能看到每次调用的输入/输出 Token 数和费用，无需应用侧额外开发 |

### D2. 具体接入方向（供后续实现参考）

1. **依赖层**：引入 `micrometer-tracing-bridge-otel`、`opentelemetry-exporter-otlp`
   （Spring Boot 3.x + Spring AI 1.x 组合下这一步基本是"加依赖 + 配置"，不用改业务代码）。
2. **配置层**：`application.yml` 里设置 `management.tracing.sampling.probability=1.0`
   （开发/演示环境全采样），`otlp` exporter 的 endpoint 指向自建 Langfuse/Grafana Tempo，
   或阿里云 ARMS 提供的 collector 地址。
3. **业务层增强（可选，锦上添花）**：给 `Orchestrator` 的每个节点方法（`jdAnalysis` /
   `resumeMatch` / ...）用 `ObservationRegistry` 手动包一层 span（或用 `@Observed` 注解），
   这样一场面试的 Trace 树会呈现出"阶段 span 包裹 LLM 调用 span"的层级结构——
   打开 Trace 详情就能直接看到"这场面试哪个阶段耗时最长、哪个 Agent 消耗 Token 最多"，
   对 Prompt 调优和成本分析都直接有用。
4. **成本看板（可选）**：把 Token 用量从 span 属性里提取出来，转成 Micrometer
   `Counter`/`DistributionSummary` 业务指标（如"单场面试总 Token 消耗"、
   "各 Agent 平均 Token 占比"），Prometheus 抓取 + Grafana 面板长期跟踪成本趋势。

**面试话术**：*"多 Agent 系统调试起来最头疼的是"看不清一次请求到底调了几次模型、
每次花了多少 Token、耗时卡在哪一步"。我没有自己写埋点代码，而是直接用 Spring AI
自带的 Observation 能力接 OpenTelemetry，导出到 Langfuse（或阿里云 ARMS 的 AI 可观测），
这样一场面试的完整调用链——7 个 Agent 节点、ReactAgent 的工具调用循环——都能在
Trace 里按时间线和层级看到，包括每一步的 Token 消耗，不需要额外开发一套监控系统。"*

### Agent 分级（重新对齐，避免把普通 LLM 调用也算成 Agent）

| 级别 | 判据 | 成员 |
|---|---|---|
| **L0 非 LLM** | 纯代码 | `IntentRouter`、`QuestionRuleChecker` |
| **L1 单轮 LLM** | 一次 `chatModel.call` + 结构化输出解析 | `JDAnalyzer`、`ResumeMatcher`、`QuestionPlanner` Phase1、Phase2 的 experience/design 兜底、`Interviewer`（×3）、`Evaluator`、`ChatAgent`、4 个 Skill |
| **L1 但独立 Agent 角色** | 单轮实现，有独立立场与结构化判定输出 | **`QuestionReviewer`** |
| **L2 Agentic** | `ReactAgent` + 工具，决策权下放模型 | **出题 Agent**（2 工具）、**`ReviewPlanner`**（4 工具 + 规则反思） |

> 能力层里的 LLM 调用（`LlmRerankStrategy`、`RagQualityEvaluator`、`QuestionParser`、
> `WebLoader`）**不应算 Agent**——它们是"用了 LLM 的工具函数"，无自主决策。

## 更新后的优先级建议

| 排序 | 条目 | 理由 |
|---|---|---|
| **1** | **D 全套（可观测性接入）** ⭐ 优先级已上升 | 原本排第 3，现在应该排第一。B1/B2/B3/B4 都已落地，但**没有任何数据能证明它们有效**——审题回环到底打回了多少题？回炉后质量真的更好吗？Router 有多少方向真的路由到了网络？这些现在只能看日志人工数。而且 D 的投入最小（基本是加依赖+配置），却能反过来给已完成的四项改造提供**量化证据**，这对简历"有数据支撑"的说服力提升最大 |
| **2** | **A1 剩余部分（Graph Checkpoint 持久化）** | 工程深度最有说服力，面试官最容易追问。目前只做了 WS 层内存态重连，"服务重启面试丢失"这个短板还在 |
| **3** | **A3（并行化）** | 纯收益零风险。而且本轮 B4 引入了审题回环，出题阶段的 LLM 调用次数明显增加（一档约 4~7 次，三档合计 12~21 次），耗时敏感度上升，并行化的收益比改造前更大 |
| **4** | **A2（隐藏分支提升为条件边）** | 本轮已经在出题子图里实践了"用条件边表达业务分支"，主流程照做的经验成本很低；且做完 A2 后接 D 的 Trace 会更好看（跳过的节点不产生 span） |
| **5** | **C1（`ChatAgent` 升级为 ReactAgent）** | 5 个 `ToolCallback` 已就绪，边际成本最低的新功能 |
| **6** | **A4（评分 Critic）** | 可直接复用 B4 经验，但"评分准不准"缺少 ground truth，建议等 D 落地有数据后再评估 |
| — | C2 / C3 | 时间充裕时的补充项 |

**一条建议**：如果只做一件事，做 **D**。现在这个项目的技术密度已经不低（Multi-Agent 回环、
