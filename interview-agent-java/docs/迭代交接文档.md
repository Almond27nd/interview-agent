## 1. 断线重连（WebSocket 层）

### 1.1 背景问题

面试流程平均耗时数分钟，全程占用一个 WebSocket 连接和一条后台线程（`asyncExecutor`）。
浏览器网络抖动、笔记本合盖、页面误刷新都会导致连接断开——如果断线直接销毁面试状态，
用户唯一的选择就是从头重来，代价很高。

### 1.2 设计

`WebSocketHandler` 用两个 Map 管理会话：

- `sessions`：按 `WebSocketSession.getId()`（连接级）索引，用于普通消息路由；
- `userSessions`：按 `userID`（用户级）索引，用于重连时"找回同一用户正在进行中的面试状态"。

`WSSession` 对象本身持有：

- `volatile WebSocketSession conn`：当前生效连接，可变，重连时只替换这个引用；
- `volatile BlockingQueue<String> answerCh`：面试线程阻塞等待用户输入的共享队列；
- 一组"重连快照"字段：`pendingQuestionNum/pendingQuestionContent/pendingQuestionAskedAtMs`
  （当前待答题目及提问时间）、`currentStage/currentStageMessage`（当前阶段）、
  `disconnectedAtMs`（断线时间点，0 表示当前连接活跃）。

**关键点**：面试运行在后台线程里，其内部闭包（`InterviewCallbacks` 匿名类）只捕获了
`WSSession` 对象本身，对外发送永远读 `ws.conn` 的*最新值*、接收回答永远读 `ws.answerCh`。
所以重连时只需要：

```java
// afterConnectionEstablished()
WSSession existing = userSessions.get(userID);
boolean resumed = existing != null && existing.interviewRunning;
if (resumed) {
    ws = existing;
    ws.conn = session;          // 只换连接引用
    ws.disconnectedAtMs = 0;
    sendResumeSnapshot(ws);     // 回放当前进度
}
```

不需要重新创建 `Orchestrator`、不需要重放整个面试流程——后台线程"无感知"地自动切换到新连接。

### 1.3 断线不等于终止：宽限期 + 定时清理

`afterConnectionClosed` 时，若面试仍在进行中，**不立即清理状态**，只记录 `disconnectedAtMs`；
后台线程仍阻塞在 `answerCh.poll()` 上等待。一个后台 `ScheduledExecutorService`
（`cleanupScheduler`，30 秒扫描一次）检查：断线超过 `reconnect-grace-seconds`（默认 300 秒）
仍未重连的会话，主动 `answerCh.offer("/quit")` 终止面试线程，避免线程/资源永久泄漏。

```java
// application.yml 可配置：
app.interview.answer-timeout-seconds: 120
app.interview.reconnect-grace-seconds: 300
```

### 1.4 重连快照回放

`sendResumeSnapshot`：若有待答题目，连同"距真正超时还剩多少秒"一起回放
（`ServerMsg.type=resumed`，`remainingSeconds` 字段）；这个剩余时间是从**原始提问时刻**算起，
不是简单把倒计时重置为完整时长——因为后端 `answerCh.poll(timeout)` 的超时计时不会被重连打断。
若当前没有待答题目（正处于 LLM 处理阶段），只回放当前 stage 提示。

前端 `chatStore.ts` 收到 `resumed` 消息后，用后端给出的精确剩余秒数校正本地倒计时 UI
（`api/ws.ts` 内建自动重连：`onclose` 时若有 token，3 秒后自动 `connect()`）。

### 1.5 为什么面试跑在独立线程池而不是 `commonPool`

`asyncExecutor = Executors.newCachedThreadPool(...)`：面试流程内部用 Spring AI Alibaba Graph
编排，graph 节点本身会提交到 `ForkJoinPool.commonPool()` 执行；而 `runInterview` 又会阻塞等待
节点完成（节点内部还会阻塞等用户回答）。如果面试线程也用 `commonPool`，两者会互相抢占导致
线程饥饿甚至死锁，所以隔离出独立可扩展线程池。

**涉及文件**：`handler/WebSocketHandler.java`（核心）、`model/ServerMsg.java`（新增
`remainingSeconds` 字段）、`interview-agent-web/src/api/ws.ts`、`interview-agent-web/src/store/chatStore.ts`

## 2. 限时答题

### 2.1 设计

每题候选人思考+作答的最长等待时间可配置（默认 120 秒），只限制"等待用户输入"这一步的阻塞
时长，不影响 LLM 出题/评分调用本身。

`HumanGate.await` 提供两种阻塞取值方式：

```java
// 无超时：用于 requestClarification 等不限时场景
public static String await(BlockingQueue<String> answerCh)

// 带超时：用于 getUserAnswer 限时答题场景
public static String await(BlockingQueue<String> answerCh, long timeout, TimeUnit unit) {
    String answer = answerCh.poll(timeout, unit);
    if (answer == null) throw new AnswerTimeoutException();
    return checkQuit(answer);
}
```

新增 `AnswerTimeoutException`（区别于 `UserQuitException`）：候选人没有主动退出，只是这一题
超时——流程应把该题按"未回答"记 0 分并继续下一题，而不是终止整场面试。

`Orchestrator.interview()` 捕获该异常：

```java
try {
    answer = c.cb.getUserAnswer();
} catch (AnswerTimeoutException e) {
    answerTimedOut = true;
    answer = "[超时未作答]";
    c.cb.onTimeout(asked);
}
// 超时的题目直接判定 0 分，不再调用 LLM 评分
score = answerTimedOut ? AnswerScore.builder().score(0).feedback("超时未作答")... : interviewer.scoreAnswer(q, answer);
```

追问环节同样捕获超时，追问答案记为 `[超时未作答]`，不阻塞流程。

前端收到 `answer_timeout` 消息后清除倒计时并提示；`resumed` 场景下的倒计时也来自同一套
超时基准，两者语义一致。

**涉及文件**：`graph/AnswerTimeoutException.java`（新增）、`graph/HumanGate.java`、
`graph/InterviewCallbacks.java`（新增 `onTimeout` 回调）、`graph/Orchestrator.java`、
`handler/WebSocketHandler.java`、`model/ServerMsg.java`（`type=answer_timeout`）、
`interview-agent-web/src/store/chatStore.ts`

## 3. 澄清追问的人工选择机制（HumanGate）

已有独立文档 `docs/clarify-human-gate.md` 详细记录，此处只给结论：

- JD 分析 / 简历匹配阶段，LLM 会对"当前信息是否足够"做语义自评；不足时暂停并
  `requestClarification` 向用户追问，最多循环 2 轮。
- 改造前：用户回复的自由文本需要再调一次 LLM 判断语义（多一次调用+误判风险）。
- 改造后：前端渲染**继续 / 补充 / 退出**三个显式选项，"继续"对应确定性哨兵值
  `HumanGate.CONTINUE_WITH_CURRENT_INFO`，后端精确字符串比较，零额外 LLM 调用。
- 该机制统一由 `requestClarification(stage, question)` 承载，按 `stage` 参数泛化，
  `jd_analysis` 和 `resume_match` 两个阶段复用同一套前后端实现，接入新阶段不需要改前端代码。

**涉及文件**：`graph/HumanGate.java`、`model/ClientMsg.java`、`handler/WebSocketHandler.java`、
`agent/JDAnalyzer.java`、`model/ResumeMatchResult.java`、`agent/ResumeMatcher.java`、
`graph/Orchestrator.java`、前端 `types/message.ts`、`components/MessageBubble.tsx`、

## 4. 短期记忆：闲聊场景的摘要滚动缓冲

### 4.1 背景问题

`ChatAgent`（WS 优先级 3 兜底的闲聊 Agent）此前的实现是"硬截断"：只取最近 N 条消息拼进
Prompt，超出窗口的早期上下文直接丢弃——用户很早提到的岗位方向、已澄清过的背景信息，
一旦被截断就再也拿不到。

### 4.2 设计：类似 LangChain `ConversationSummaryBufferMemory`

新增 `agent/ChatMemory.java`：

```java
public class ChatMemory {
    private final List<Message> history = new ArrayList<>(); // 近期原始消息，不压缩
    private String summary = "";                              // 更早消息折叠后的滚动摘要
}
```

`ChatAgent.chat(memory, userInput)` 每轮结束把 `(userInput, reply)` 追加进 `history`，
超过 `MAX_RAW_MESSAGES=20` 条（10 轮对话）时触发 `compressIfNeeded`：

```java
int foldCount = history.size() - KEEP_RECENT_MESSAGES; // 保留最近10条(5轮)
List<Message> toFold = history.subList(0, foldCount);
// 旧摘要 + 待折叠消息 → 一次 LLM 调用 → 新摘要（融合，不是替换）
memory.setSummary(llmSummarize(prevSummary, toFold));
history = 剩余的最近消息;
```

摘要调用失败时降级为直接截断丢弃（保证 `history` 不会无限增长，不影响主流程）。

调用方（`WebSocketHandler.WSSession.chatMemory`）只需持有同一个 `ChatMemory` 实例反复传给
`ChatAgent#chat`，不需要自己管理历史的增删——增删逻辑完全封装在 `ChatAgent` 内部。

**涉及文件**：`agent/ChatMemory.java`（新增）、`agent/ChatAgent.java`

## 5. 长期记忆：让"记忆"真正被业务消费

Go 版本已有 `UserProfile`（`skillLevel`/`weakPoints`/`interviewHist`）的数据结构和存储，
但本轮迭代补上了两处此前"建了字段但从未写入/读取"的空缺，并新增了跨会话的历史面试趋势感知。

### 5.1 技能等级回填（`skillLevel` 此前永远是空 map）

`memory/LongTermMemory.updateSkillLevels(userID, skillScores)`：面试结束后，按题目的
`skills` 标签把本场问答分组聚合出每个技能的平均分，映射为
`beginner(<60) / intermediate(60~80) / advanced(>=80)` 写回画像：

```java
// Orchestrator.reviewPlan() 里聚合调用
Map<String, List<Double>> skillScores = new HashMap<>();
for (QAPair qa : qaHistory) {
    for (String skill : qa.getQuestion().getSkills()) {
        skillScores.computeIfAbsent(skill, k -> new ArrayList<>()).add(qa.getScore());
    }
}
longTermMem.updateSkillLevels(userID, skillScores);
```

策略与 `updateWeakPoints`（用最新得分覆盖）保持一致，不做跨场次滑动平均。

### 5.2 出题规划：跨岗位打通的历史薄弱点

`Orchestrator.questionPlan()` 读取 `longTermMem.getWeakPoints(userID)`（已按"超过 30 天淘汰
+ 分数排序 + Top 10"处理），**不再硬性过滤掉与当前 JD 不相关的薄弱点**，而是分两组：

```java
// 与当前 JD 技能强相关的放前面、标"[强相关]"；跨岗位的也保留，标"[其他岗位历史薄弱点，供参考]"
for (WeakPoint wp : weakPoints) {
    (isWeakPointRelevant(wp.getTopic(), jdSkills) ? relevant : others).add(wp);
}
```

例如候选人面过"Java 后端"又面"Go 后端"，"分布式系统设计"这类跨岗位共性薄弱点也能被
`QuestionPlanner.planDirections` 的 Prompt 感知到。

### 5.3 出题规划：同岗位历史面试趋势（跨会话）

新增 `MySQLStore.getRecentInterviewRecords(userId, position, limit)`：查询该用户针对**同一岗位**
最近几场面试的摘要（`session_id/position/overall_score/created_at`）。
`Orchestrator.buildInterviewHistoryContext` 把记录按时间正序组装成带分差的自然语言：

```
- 第 1 次（2026-06-01）：综合得分 55
- 第 2 次（2026-06-15）：综合得分 68（较上次+13分）
```

传入 `QuestionPlanner.planDirections` 的 Prompt，指导 LLM："若分数已持续进步，对应领域适度
提高难度、避免重复过于基础的方向；若持续低迷，保留/加强该领域方向以验证薄弱点是否真正改善"。

### 5.4 复习计划：参考上一次同岗位的计划

新增 `MySQLStore.getLatestReviewPlanJson(userId, position)`：查询该用户同岗位最近一次生成的
`review_plan_json`。`Orchestrator.reviewPlan()` 把它连同本场评估报告一起传给
`ReviewPlanner.plan(report, previousPlanJson)`，Prompt 里要求"若薄弱领域已改善则不重复推荐、
若依旧存在则可保留/深化上次计划，避免推荐完全重复的资源链接"。

### 5.5 存储层：Redis 缓存 + MySQL 持久化组合存储

`memory/CombinedStore`：

- **写**：先写 MySQL（持久化），再写 Redis（缓存，失败不影响主流程）；
- **读**：先读 Redis，miss 则读 MySQL 并回填 Redis。

`MySQLStore` 用 `JdbcTemplate` 在 `@PostConstruct` 里显式建表（`user_profiles` /
`interview_records`）——因为这两张表是原生 SQL 操作的非实体表，Spring Data JPA 的
`ddl-auto` 只处理 `@Entity` 的 `users` 表；用 `JdbcTemplate` 执行 DDL 是为了避免
`@PostConstruct` 上 `@Transactional` 自调用代理不生效导致的 `TransactionRequired` 问题。

**涉及文件**：`memory/LongTermMemory.java`、`memory/MySQLStore.java`、`memory/CombinedStore.java`、
`memory/RedisStore.java`、`memory/UserProfile.java`、`graph/Orchestrator.java`（`questionPlan`/
`reviewPlan` 两处）、`agent/QuestionPlanner.java`（Prompt 新增历史趋势参数）、
`agent/ReviewPlanner.java`（Prompt 新增 `previousPlanJson` 参数）

## 6. 用户认证（JWT）

`auth/` 包：`JwtService`（注册/登录/生成校验 token，HMAC-SHA256，密钥不足 32 字节自动补齐）、
`AuthController`（`POST /api/register`、`POST /api/login`）、`UserEntity`（JPA 实体，
密码用 `PasswordEncoder` bcrypt 哈希）、`UserRepository`。

`WebSocketHandler.afterConnectionEstablished` 从连接 URL 的 `?token=` 中取出 JWT 并校验，
成功则 `userID` 为对应用户名，否则降级为 `"anonymous"`（匿名用户不启用断线重连——
`userSessions` 只索引非匿名用户，见第 1 节）。

`InterviewHistoryController` 由于全局 `SecurityConfig` 对 `/api/**` 是 `permitAll`
（没有全局 JWT 过滤器），手动解析 `Authorization: Bearer <token>` 头做校验，与 WS 层的
认证方式保持一致（同一份 `JwtService.validateToken`）。

**涉及文件**：`auth/JwtService.java`、`auth/AuthController.java`、`auth/UserEntity.java`、
`auth/UserRepository.java`、`handler/WebSocketHandler.java`、

## 7. 历史面试查询能力

### 7.1 REST API

`handler/InterviewHistoryController.java`：

- `GET /api/interviews`：最近 20 场面试摘要列表；
- `GET /api/interviews/{sessionId}`：单场详情，解析 `report_json`/`review_plan_json`
  为结构化对象，**同时给出与实时 WS 推送一致的 Markdown 渲染结果**
  （`Evaluator.formatReport` / `ReviewPlanner.formatReviewPlan`），前端可直接复用
  `ReportCard`/`ReviewPlanCard` 组件展示，不用为历史详情页重新实现一套排版逻辑；
  同时用 `userId` 过滤，防止越权查询他人 session。

前端 `HistoryModal.tsx` 消费这两个接口。

### 7.2 聊天入口：关键词意图路由（IntentRouter 增强）

用户在闲聊里问"看下历史/上次面试记录"，纯聊天走 LLM 兜底根本感知不到这个能力。
`WebSocketHandler.handleChat` 在"优先级 3 ChatAgent 兜底"之前插入一层
"优先级 2.5：`IntentRouter.route`"：

```java
switch (intentRouter.route(input, ws.interviewRunning)) {
    case INTENT_VIEW_HISTORY -> 直接回复 buildHistoryReply(ws.userID)（查 MySQLStore 最近 5 场）;
    case INTENT_UPLOAD_RESUME -> 提示走"开始面试"表单，而非聊天框直接粘贴;
    case INTENT_UPLOAD_JD    -> 同上;
    default -> 落到 ChatAgent 兜底;
}
```

只拦截"当前系统确有对应能力、但纯 LLM 聊天感知不到"的意图，`start_interview`/普通闲聊仍
交给 `ChatAgent`（其 Prompt 已内置引导用户点击按钮的话术，见第 4 节）。

**涉及文件**：`handler/InterviewHistoryController.java`（新增）、`agent/IntentRouter.java`、
`handler/WebSocketHandler.java`（`buildHistoryReply`）、前端 `HistoryModal.tsx`

## 8. 评估报告：风格一致性观察（`anomaly_notes`）

`Evaluator` 的评估 Prompt 新增 `anomaly_notes` 字段：要求 LLM 纵览候选人从第一题到最后一题的
整体作答风格（用词习惯、回答深度、结构完整度），若某一题/几题明显偏离候选人自身整体风格
（例如前几题简短口语化，某题突然变成教科书级表述），客观描述这个差异点，**不下结论说
"作弊"**；整体风格一致则返回空数组。`formatReport` 渲染为"⚠️ 风险提示（风格一致性观察，
仅供参考）"，明确标注"不代表作弊结论，仅供面试官复核时参考"。

这是一个"提示不判定"的设计取舍：LLM 无法可靠判断作弊，但可以可靠地描述"风格差异"这个
客观现象，把最终判断权交还给人。

**涉及文件**：`agent/Evaluator.java`、`model/EvaluationReport.java`

## 9. 唯一的 ReactAgent：`ReviewPlanner`

全项目其余 Agent（`JDAnalyzer`/`ResumeMatcher`/`QuestionPlanner`/`Interviewer`/`Evaluator`/
`ChatAgent`）都是单轮 LLM 调用（一次 Prompt → 一次结构化输出）。只有 `ReviewPlanner` 用
Spring AI Alibaba 的 `ReactAgent` 实现真正的工具调用循环：

```java
ReactAgent agent = ReactAgent.builder()
        .name("review_planner")
        .model(chatModel)
        .instruction(REVIEW_PLANNER_INSTRUCTION)
        .tools(gitHubTool != null ? List.of(gitHubTool.asToolCallback()) : List.of())
        .build();
AssistantMessage msg = agent.call(userMsg);
```

模型根据面试评估报告的薄弱点，自主决定是否、用什么英文关键词调用 `search_github_repos`
工具去找真实开源项目/教程，写进推荐资源（`type=repo`，`url` 用真实搜索结果，工具不可用/
无结果时不编造链接）。`ReactAgent` 执行失败时降级为不带工具的单轮生成（`generateWithReactAgent`
返回 `null`，退回 `chatModel.call`），保证复习计划这一步不会因为工具调用异常而让整场面试
失败在最后一步。

**涉及文件**：`agent/ReviewPlanner.java`、`mcp/GitHubTool.java`

## 10. 通用工程能力（贯穿多个 Agent）

### 10.1 `AgentUtils.callWithRetry`：统一重试

整个面试流程有 6~7 个 LLM 调用节点，链路很长，任意一个节点因网络抖动/LLM 偶发返回不合规
JSON/限流失败，都会导致耗时数分钟的整个流程从头报错。`callWithRetry(stepName, maxAttempts, action)`
统一在框架层做自动重试（默认 3 次），重试耗尽后抛 `AgentCallException`（`WebSocketHandler`
捕获后提示用户"可直接重新点击开始面试重试"，而不是笼统报"程序异常"）。

评分（`Interviewer.scoreAnswer`）额外做了"重试耗尽后降级为默认分数、不中断面试"的兜底——
因为此时候选人已经在等下一题，让整场面试因一次评分失败崩掉代价远大于给一个保守默认分。

### 10.2 阶段化取题调度 `StageScheduler`（纯逻辑，无 IO，可独立测试）

面试分 `basic(8题) → experience(5题) → design(2题)` 三阶段顺序进行，每阶段独立维护
"当前难度 + 连对/连错计数"，**进入新阶段时难度重置为 medium，不继承上一阶段**。
把这套调度逻辑从 `Orchestrator.interview()` 的 IO（提问/评分/回调）中剥离成独立类，
便于单元测试覆盖调度算法本身。

### 10.3 候选人画像异步更新链（不阻塞下一题）

画像文本只是 `Interviewer.askQuestion` 的软上下文（影响提问措辞语气），不参与选题/难度调节。
`Orchestrator.Ctx.profileUpdateChain` 把同一场面试内的多次"调 LLM 重新生成画像"串成一条
`CompletableFuture` 链，依次在独立线程池 `profileUpdateExecutor` 上执行——既不阻塞主线程问
下一题，又保证多次更新按发生顺序生效，不会因并发写导致"后完成的旧结果覆盖先完成的新结果"。

**涉及文件**：`agent/AgentUtils.java`、`graph/StageScheduler.java`、`graph/Orchestrator.java`

## 12. 已知限制 / 后续可做（详见 `优化路线图与简历亮点方案.md`）

- 断线重连**只支持同一后端实例内**（`userSessions` 是内存 Map，多实例部署时需要引入
  外部 checkpoint/状态存储才能跨实例恢复）；
- 限时答题的超时基准依赖 `answerCh.poll(timeout)`，服务重启会导致进行中的面试丢失

- `ReviewPlanner` 是全项目唯一 ReactAgent，其余均为单轮 LLM 调用，RAG 检索管道仍是手写
  pipeline（未做成 Agentic RAG）；
  > ✅ **本条已在第 14 章被取代**：现在 ReactAgent 有两个（`ReviewPlanner` + 出题 Agent），
  > basic 类方向的题库检索已改造为 Agentic RAG（Router + Corrective + Critic 回环）。
  > 仍然成立的部分：experience/design 类方向的出题、以及 basic 类降级路径，还是手写 pipeline。
- 长期记忆的 `updateWeakPoints`/`updateSkillLevels` 都是"用最新得分覆盖"的简化策略，
  未做跨场次滑动平均；
- 目前没有接入 APM/可观测性平台（Langfuse/OpenTelemetry 等），LLM 调用链路的 tracing

1. 开一场面试，中途关闭浏览器标签重新打开（同账号 token）→ 应自动重连并恢复到当前题目，

   刷新页面后面试状态应视为丢失（符合预期）。

## 14.1 改动一：Router 升级（新增网页检索源）

### 背景问题

**分类层面**：升级前出题 Agent 面前只有 1 个工具，所有决策都在"这一个来源的结果能不能用"
这个层面。按 Agentic RAG 综述（Singh et al., *Agentic RAG: A Survey*）的分类标准，这只算
**Corrective/Self-Reflective** 子类型，**够不上 Router**——Router 特指"面前有 ≥2 个异构
检索源，agent 要先决定路由到哪一个"。

**业务层面**：题库覆盖的是候选人专属的固定题目集合。遇到**冷门/新出现的技术点**（某框架的
新版本特性、小众开源项目）时，题库检索不到、模型自身知识也可能过时，容易凭空编造错误细节。

### 新增 `mcp/WebSearchTool.java`

**检索源选型：博查AI搜索**（`api.bochaai.com/v1/web-search`）而非更常见的 Tavily。
理由：项目其余外部依赖（DashScope、Milvus）都是国内可直连服务，检索源延续同一原则，
避免引入跨境访问不稳定的风险——这是个真实的工程约束，不是技术偏好。

实现：Java 11 原生 `HttpClient` 发 POST，Jackson 解析 `data.webPages.value[]`
（`name`/`url`/`summary`）；连接超时 5s、请求超时 10s。

**复用 `GitHubTool` 的三处健壮性写法**：

| 设计 | 目的 |
|---|---|
| 本地缓存（`ConcurrentHashMap` + 10 分钟 TTL） | 同一关键词短时间内不重复打外部 API |
| **"查无结果" vs "工具故障" 分开提示** | 网络异常时明确告知模型"工具当前不可用，别再重试，直接结合已有知识出题"——避免模型把**临时故障**误判为"这个技术点没资料"而反复重试 |
| 故障响应不进缓存 | 避免短暂抖动被当成长期结论缓存 10 分钟 |

**可选工具模式**（与 `GitHubTool` 同一套）：

```java
@Component
@ConditionalOnProperty(prefix = "app.websearch", name = "api-key", matchIfMissing = false)
public class WebSearchTool { ... }
```

不配 `BOCHA_API_KEY` 这个类**根本不注册成 Spring Bean**，`QuestionPlanner` 里的
`@Autowired(required = false)` 字段自动是 `null`，出题 Agent 退化为单来源版本。
**不因为多加一个工具而让主流程变脆弱。**

### `QuestionPlanner` 的路由接线

把原来一段固定 instruction **拆成 4 段模板常量**，按 `hasWebSearch` 动态拼接：

```java
private static String buildGroupAgentInstruction(boolean hasWebSearch) {
    if (hasWebSearch) {
        return BASE + WEB_PART + TAIL_COMMON + OUTPUT_WITH_WEB;
    }
    return BASE + TAIL_COMMON + OUTPUT_NO_WEB;
}
```

| 片段 | 内容 |
|---|---|
| `BASE` | 题库工具说明（首选/权威来源） |
| `WEB_PART`（可选） | 网页工具说明 + 触发路由的两个条件 |
| `TAIL_COMMON` | `direction_index` 回填规则、方向数量必须对应等通用约束 |
| `OUTPUT_WITH_WEB` / `OUTPUT_NO_WEB` | 输出 JSON schema，前者 `source` 多了 `web:<链接>` |

> **⚠️ 后续维护关键约束**：发给模型的工具能力描述必须与实际绑定的 `tools` 列表严格一致。
> 两处判断都用**同一个** `hasWebSearch` 变量，否则会出现"指令里提到了 `search_web`，
> 但工具列表里没挂"，模型尝试调用不存在的工具而报错。

**路由边界完全靠 prompt 工程实现，代码里没有一行 if-else。** `WEB_PART` 里显式写了两个
必要条件：题库换词重试后仍未命中 + 属于模型自己把握不准的新/冷门技术点；并明确
`search_web` 只用于查证事实、不能拿网页内容直接当题目照搬。

### 输出协议扩展

`source` 从两种取值扩展为三种：

| source | 含义 |
|---|---|
| `题库原题ID` | 直接用题库原题（`content` 完全照搬） |
| `web:<链接>` | 题库未命中 + 冷门技术点，路由到网络查证后自己组织出题 |
| `llm` | 两个来源都没查（或不需要查），依据参数化知识自行出题 |

回填逻辑不需要改（按 `direction_index` 精确对应，`source` 只是多了一种字符串格式）。

### 一个容易被追问的点：两个工具性质不同

| Tool | 是严格 RAG 吗 | 原因 |
|---|---|---|
| `search_question_bank` | **是** | 检索出的内容可**直接当最终答案**（原题照搬） |
| `search_web` | **不是** | 检索出的是**辅助查证信息**，不能直接当答案，模型仍需自己组织生成 |

## 14.2 改动二：Multi-Agent 审题回环（B4）

### 背景问题

改动一之后仍是 Single-Agent，**出题者同时充当自己的质检员**，两层问题：

**动机层面：确认偏差。** 同一个 agent 评价自己刚写的题，几乎总说没问题（LLM 自评的已知
失败模式，也是 Reflexion / Constitutional AI 要引入独立 Critic 的原因）。

**能力层面（更硬）：有几类缺陷它结构上就发现不了。**

| 缺陷 | 为什么发现不了 |
|---|---|
| 跨方向重复 | 题库检索**逐方向独立**进行，"MySQL索引优化"和"MySQL B+树"很容易命中实质相同的原题，但它的注意力一直在"逐个查库"，不会回头做全局比对 |
| 难度名不副实 | 题库原题的 `difficulty` 是**题库自己标的**，照搬进来可能一个 hard 方向拿到只考 API 用法的题，直接破坏 `StageScheduler` 依赖的难度梯度与 `adjustDifficulty` 的动态调节 |
| 事实性风险 | `source=web` 依据网页摘要（可能过时片面），`source=llm` 可能幻觉，自己校验自己不可靠 |
| 追问不递进 | `follow_ups` 该比主问深一层，不该换个说法重复问 |

### ⚠️ 一个被否决的方案（后续维护者请勿"改回去"）

先评估过更"教科书"的 **Retriever + Generator** 拆法（即 `B1升级` 文档第 9 节自己埋的
"下一步"建议），**最终否决**：

题库检索命中时指令要求"原题照搬不得改编"，Generator 拿到 evidence 后几乎没有生成空间，
只剩补追问、整理参考答案这类格式化工作。一档 5 个方向 3 个命中的典型情况下，
**两个 agent 职责重叠在"出题"上**，说不清第二个 agent 的价值。

| | Retriever + Generator | **Assembler + Critic（采用）** |
|---|---|---|
| 职责重叠 | 有（题库命中时近乎透传） | 无（生成 vs 批判，天然对立） |
| 回环 | 单向流水线 | 天然双向 |
| 现有代码改动 | 大（现有 agent 拆两半、instruction 重写） | 小（现有 agent 完全不动） |
| 实际质量收益 | 不明显 | 明显 |
| 论文背书 | RAG 两段结构 | Reflexion / Constitutional AI / Actor-Critic |

### 架构：一档一张带回环的 StateGraph

```
START → assemble ──→ review ──[无打回 或 轮次耗尽]──→ finalize → END
           ↑            │
           └────────────┘  [有打回 且 round < MAX_REVIEW_ROUNDS(2)]
```

`review` 节点内部是**两级串联**：先跑零 token 的规则预检，再跑语义批判的审题 Agent。

**四个参与者，只有两个是 Agent**（这点容易被误解）：

| 参与者 | 是 Agent | 有 LLM | 职责 |
|---|---|---|---|
| `StateGraph` | ❌ | ❌ | 流程控制、条件回环判定（纯代码，无智能） |
| **Agent① 出题** `question_assembler_group` | ✅ | ✅ | 检索、选源、出题、按理由重出 |
| `QuestionRuleChecker` | ❌ | ❌ | 机械可判定的硬错误（`final` 静态工具类，非 Bean） |
| **Agent② 审题** `QuestionReviewer` | ✅ | ✅ | 语义批判 |

### 三层图嵌套（同一引擎三种粒度）

```
第1层  Orchestrator 面试全流程图（6阶段，纯 DAG）
         └─ question_plan 节点内
第2层      出题-审题协作图（assemble ⇄ review → finalize，带回环）  ★ 本轮新增
             ├─ assemble 内跑 Agent①
第3层          └─ Agent① 自己的 ReAct 循环图（llm ⇄ 题库/网络工具）
             └─ review 内跑规则预检 + Agent②（单轮，无图）
```

### 设计决策 ①：为什么插一层纯 Java 规则预检

缺陷分两类：**机械可判定**（难度不一致、`follow_ups`/`reference`/`source` 缺失、题干过短、
跨方向文本近重复）和**必须理解语义**（考点跑偏、难度名不副实、追问不递进、事实存疑、
语义重复）。

剥离前者的三个收益：**省 token**、**零误判**（LLM 判重有随机性，bigram Jaccard 是确定的）、
**Critic 的 prompt 更专注**。

思路复用自 `ReviewPlanner` 的 B2 反思循环（`findUncoveredHighPriorityAreas`），这次抽成了
可独立单测的组件。

### 设计决策 ②：重复判定阈值 0.6 —— 一个被测试暴露出的真实边界（勿轻易调低）

用**字符 bigram 的 Jaccard 相似度**，而非整串相等或编辑距离：中文题干"MySQL 索引失效的
场景有哪些"和"哪些场景会导致 MySQL 索引失效"是同一道题的不同措辞，整串比对判不出来，
bigram 集合重叠度能捕捉同义换序，且对长度差异不敏感。

**落地时实测：上面那对句子相似度只有约 0.5，低于 0.6 阈值，规则层不会报。**

> **这不是 bug 而是刻意取舍**，已固化成显式测试 `check_reorderedDuplicate_leftToCritic`：
> 调低阈值能抓住它，但会开始误伤考点相邻但确实不同的题目。而**误判代价比漏判更高**——
> 合格的题被白白重出，既烧 token 又可能越改越差。这类"措辞不同、考点相同"的语义重复
> **故意留给 Critic**。
>
> **分层的本质：规则层要零误判，Critic 负责理解语义。**
> 后续维护者若看到"某个明显重复没被规则层拦下"，请先确认它是否属于语义重复范畴，
> 不要直接下调 `DUPLICATE_THRESHOLD`。

### 设计决策 ③：通信机制两个通道

**横向（跨 Agent）—— Blackboard 模式**，以 `direction_index` 作 join key：

```java
// model/QuestionDefect.java
{ directionIndex: 2, origin: RULE|CRITIC, reason: "...", suggestion: "..." }
```

规则层与 Critic 的输出归一化成同一结构，合并后统一回喂，出题 Agent 无需关心某条意见
来自哪一层。

> **为什么不用 agent 间自然语言对话**：出题是确定性生成任务，需要可校验、可精确回填的
> 结构化数据。走自然语言的话，模型说"第三道题有问题"，代码无法确定它数的是哪一道；
> 而 `direction_index=2` 是无歧义的。

**纵向（单 Agent 跨轮）—— 对话历史累积**：回炉时**必须复用同一个 agent 实例 + 累积的
`List<Message>`**（`GroupCtx.history`），而不是 new 新实例。新实例看不到自己上一轮的产出，
只能凭理由瞎猜。写法与 `ReviewPlanner.generateWithReactAgent` 的 B2 反思循环一致。

### 设计决策 ④：业务对象不能进 Graph State（沿用 Orchestrator 的既有坑）

graph 执行节点前会对 `OverAllState` 做序列化快照，所以 state 只放纯数据：

```java
keys.put("round", new ReplaceStrategy());
keys.put("defect_count", new ReplaceStrategy());
```

`ReactAgent` 实例、`Message` 历史、草稿全放闭包捕获的 `GroupCtx`——与 `Orchestrator.Ctx`
同一套规避手法。

### 设计决策 ⑤：刻意没用框架的 Supervisor 父子 agent 机制

`javap` 确认框架确实支持两种父子机制：`ReactAgent$AgentSubGraphNode`（agent 当子图节点）、
`AgentTool$AgentToolExecutor`（agent 包装成 `ToolCallback`，即 Supervisor 模式）。

**否决的三个理由**（后续若想改成 Supervisor，请先想清楚这三点）：

1. **又回到"自己决定要不要被审"**——调不调 Critic 由出题 agent 判断，它完全可以不调，
   正好绕开了要解决的确认偏差
2. **审核结论会退化成自然语言**，被父 agent 自由解读；现在是代码解析成结构化
   `QuestionDefect`，再由代码决定重出哪些方向
3. **轮次不可控**——`MAX_REVIEW_ROUNDS=2` 交给模型自觉遵守不可靠，写在条件边里是硬保证

> **核心原则：审核的"是否发生、发生几次、结论怎么解析"三件事收归代码硬保证；
> 只把"检索什么、怎么出题、判不判合格"这类真正需要智能的判断交给模型。**

### 关键工程约束（六条，改代码前请逐条确认）

| # | 约束 | 理由 |
|---|---|---|
| 1 | **只回炉被打回的方向**，已 pass 的不动 | 省 token、省检索调用，避免重出时把好题改坏 |
| 2 | 重出消息里**明确鼓励重新调用检索工具** | 这是回环的真实价值：打回理由能驱动**新一轮检索**（如"与方向1重复"促使换关键词重查），而不只是重写文本 |
| 3 | **`source` 诚实性底线**：改编了题干必须把 source 改成 `llm` | `Orchestrator.buildWeakReviewContent` 依据 source 回题库取参考答案做低分题巩固，一旦题干被改却仍标题库 ID，取回的答案就和题目对不上。**这是引入回环后新出现的风险点** |
| 4 | `MAX_REVIEW_ROUNDS = 2`（与 `ReviewPlanner.MAX_REFLECT_ROUNDS` 一致） | LLM 做 Critic 时"总能再挑出点毛病"，不截断会无限回炉、token 爆炸 |
| 5 | **全程 fail-open** | 审题是**质量增强**不是**准入门槛**，绝不能因为 Critic 挂了就让面试没题可问 |
| 6 | Critic instruction 里的**审核纪律**段落 | 显式给"全部判 pass 是完全正常且值得肯定的结果"的许可，抑制 LLM 做 Critic 时的过度严苛倾向；并禁止"质量不高""建议优化"这类空话（空话无法回喂） |

**两个 Agent 生命周期刻意不对称**：

| | Agent① 出题 | Agent② 审题 |
|---|---|---|
| 实例 | 图开始前建一次，跨轮**复用** | 每次 `review()` 内部**新建** |
| 对话历史 | 跨轮**累积** | **不保留** |
| 状态 | 有状态（必须记得上一轮写了什么） | 无状态 |

> Agent② 无状态是**主动选择**：带历史会产生**锚定效应**——"我上轮说这题有问题，这轮不好
> 意思说没问题了"，甚至继续挑新毛病自我印证。每轮以全新无偏视角只看当前草稿，判断更干净。

**Fail-open 全清单**：

| 失败点 | 行为 |
|---|---|
| Critic 调用异常 / 输出无法解析 | 返回空缺陷列表，视为全档通过，打 warn |
| Critic 打回但未给理由 | 忽略该条（无法回喂给出题者） |
| Critic 返回非法 `direction_index` | 忽略该条 |
| 重出时 Agent① 调用失败 | 保留上一轮草稿 |
| 轮次耗尽仍有打回 | 采纳当前版本，日志记录未消化意见数便于复盘 |
| 整张图抛异常 | 返回空 map，`Orchestrator` 整组降级为传统 pipeline |
| 某方向未被覆盖 | **只有这一个**方向走传统 pipeline，不拖累整组 |

### 完整数据链路（一档 hard，5 个方向）

**Round 1**

| 步骤 | 发生了什么 |
|---|---|
| `assemble` | Agent① 一次会话内对 5 个方向依次决策：0/1/3 命中题库原题，2 查库两次未中→路由 `search_web` 查证后自出，4 无结果自出 → 写入 `ctx.drafts` |
| 规则预检 | 方向3 `follow_ups` 为空 → 1 条 `RULE` 缺陷 |
| Critic | 方向2 标 hard 但实际只考 API 用法（难度虚高）、方向4 与方向1 语义重复 → 2 条 `CRITIC` 缺陷 |
| 条件边 | 缺陷非空（2/3/4）且 `round=1 < 2` → 回 `assemble` |

**Round 2**

| 步骤 | 发生了什么 |
|---|---|
| `assemble` | **只把 2/3/4 + 各自理由**追加进 history 重出（0/1 完全不动）。方向4 因"与方向1重复"**换关键词重新调 `search_question_bank`**；方向2 重组为考底层实现；方向3 补追问 |
| `review` | 规则层与 Critic 均无异议 |
| 条件边 | 无缺陷 → `finalize` |

**finalize**：按 `direction_index` 回填成 `Map<Integer, PlannedQuestion>` 返回。未覆盖的
下标照旧由 `Orchestrator` 走传统 pipeline 降级。

**数据形态流转**：

| 环节 | 形态 |
|---|---|
| 入参 | `List<QuestionDirection>` |
| Agent① 输出 | JSON `{"questions":[{"direction_index",...,"source"}]}` |
| 解析后 | `ctx.drafts: Map<Integer, PlannedQuestion>` |
| 规则层输出 | `List<QuestionDefect>`（`origin=RULE`） |
| Critic 输出 | JSON `{"reviews":[{"direction_index","verdict","reason","suggestion"}],"global":{...}}` |
| 解析后 | `List<QuestionDefect>`（`origin=CRITIC`，只取 `verdict=reject`） |
| 合并 | `ctx.defects`（两类混合） |
| 回喂 | `buildReworkMessage()` 按 `directionIndex` 分组渲染成自然语言 |
| 出参 | `Map<Integer, PlannedQuestion>`（与升级前完全一致） |

## 14.3 改动三：Critic 实现精简（`ReactAgent` → 单轮调用）

初版 Critic 用了 `ReactAgent` + 空工具列表（`.tools(List.of())`），理由是"写法统一"——
这个理由站不住，已改掉。

**用 `ReactAgent` 包空工具列表的四条实际代价**：

1. **多建一张 `StateGraph`**：`ReactAgent` 构造时 `initGraph()` 建 llm/tool 节点与边再
   `compile()`；而 Critic 每轮新建实例，这个开销每轮都要付一次
2. **多绕一层 graph runner**：进 runner → llm 节点 → 判断有无 tool_calls（必然没有）→ END，
   中间逻辑全是空转
3. **多一层异常包装**：真实的模型调用异常被 `GraphRunnerException` 包在外面，排查多一跳
4. **误导读者**：看到 `.tools(List.of())` 会以为这里需要工具调用能力

**改后**（与 `JDAnalyzer` / `Evaluator` 等单轮 Agent 同构）：

```java
Prompt prompt = new Prompt(List.of(
        new SystemMessage(REVIEWER_INSTRUCTION),
        new UserMessage(buildReviewPayload(dirs, drafts))
));
ChatResponse response = chatModel.call(prompt);
```

### ⚠️ 一个重要的概念澄清

**不能因为它变成单轮就说它"不是 Agent"。**

> **"是不是 Agent"取决于决策权和角色定位，不取决于用了框架里哪个类。**

它有自己的 instruction、独立的批判立场、结构化的判定输出、与出题 Agent 构成真实的协作
回环——**是一个独立的 Agent 角色**，只是它的决策不需要多轮工具循环来支撑。

按两个维度分开看更准确：

| Agent | 独立角色 | 需要 ReAct 循环 | 实现 |
|---|---|---|---|
| 出题 Agent | ✅ | ✅ 要反复调检索工具、依结果决定换词或换源 | `ReactAgent` |
| 审题 Agent | ✅ | ❌ 判断全在 context 里，一次就够 | 单轮 `chatModel.call` |
| 复习规划 Agent | ✅ | ✅ 要自主选用 4 个工具 | `ReactAgent` |

反过来也解释了**为什么出题 Agent 必须是 `ReactAgent`**：它要在一次会话里对多个方向反复
调用检索工具、依据返回结果决定是否换词重试或改用另一个数据源，这正是 ReAct 循环存在的意义。

| `agent/QuestionReviewer.java` | 改为单轮调用，移除 `ReactAgent` import，类注释新增"为什么用单轮"一节 |
| `docs/B4升级-MultiAgent出题审题回环.md` | 新增 6.1 节记录取舍，同步修正三处相关表述 |

## 14.5 Agent 分级现状（交接后重新对齐认知）

本轮之后，"项目里有几个 Agent"这个问题需要按级别回答，避免把普通 LLM 调用也算成 Agent：

| 级别 | 判据 | 成员 |
|---|---|---|
| **L0 非 LLM** | 纯代码，无模型调用 | `IntentRouter`（关键词匹配）、`QuestionRuleChecker`（规则预检） |
| **L1 单轮 LLM** | 一次 `chatModel.call` + 结构化输出解析，无工具无循环 | `JDAnalyzer`、`ResumeMatcher`、`QuestionPlanner` Phase1、`QuestionPlanner` Phase2 的 experience/design 兜底、`Interviewer`（提问/评分/追问 三个独立单轮）、`Evaluator`、`ChatAgent`、4 个 Skill |
| **L1 单轮但独立 Agent 角色** | 单轮实现，但有独立立场与结构化判定输出 | **`QuestionReviewer`**（审题） |
| **L2 Agentic** | `ReactAgent` + 工具，决策权下放给模型 | **出题 Agent**（题库 + 网络）、**`ReviewPlanner`**（4 个工具 + 规则反思循环） |

**能力层里的 LLM 调用不应算 Agent**（它们是"用了 LLM 的工具函数"，无自主决策）：
`LlmRerankStrategy`、`RagQualityEvaluator`、`QuestionParser`、`WebLoader`。

**Multi-Agent 在项目里有两种形态，含金量不同**：

| | 形态 A：宏观流水线（`Orchestrator`，一直就有） | 形态 B：微观回环协作（出题环节，★ 本轮新增） |
|---|---|---|
| 协作方式 | 顺序流水线，前一个产物是后一个输入 | 生成 vs 批判，两个立场对立的角色 |
| 传递媒介 | `Orchestrator.Ctx` 闭包持有者 | `QuestionDefect` 结构化缺陷（Blackboard） |
| 有回环 | ❌ 纯 DAG，只有"提前终止"条件分支 | ✅ 条件边 `review → assemble` |
| 角色间信息交换 | 单向传数据，不互评 | ✅ 审核意见反馈驱动重出 |
| 一方能影响另一方**行为** | ❌ | ✅ 打回理由能驱动**重新检索** |
| 权限差异化 | ❌ | ✅ 检索权只归出题者，判断权只归审题者 |
| 定性 | 本质是**编排**（Orchestration） | 真正的**协作**（Collaboration） |

3. **观察出题日志**应能看到三类记录：
   - `出题 Agent 第 N 轮...完成，本轮产出 X 道题（累计覆盖 X/Y）`
   - `第 N 轮审题：规则层 X 条 + 审题 Agent Y 条，共打回 Z 个方向`
   - `分组出题定稿（难度X）：共 N 道题，经历 M 轮出题-审题`
4. **人为制造回环**：临时把 `QuestionRuleChecker.MIN_CONTENT_LENGTH` 调大（如 200），
   应观察到所有方向被打回、第 2 轮重出、第 2 轮后仍不达标则 fail-open 采纳当前版本
   （日志出现"审题轮次已达上限"）。**测完记得改回。**
5. **验证 fail-open**：临时让 `QuestionReviewer.review` 首行抛异常 → 出题流程应正常完成，
   日志出现"审题失败，本档视为全部通过（fail-open）"，面试照常进行。**测完记得改回。**
6. **验证 source 诚实性**：检查最终题目里 `source` 为题库 ID 的题，其 `content` 应与题库
   原题完全一致（可在 Milvus / 题库文件里对照）；若发现被改编过却仍标题库 ID，说明重出
   指令的第 2 条约束失效，会导致低分题巩固环节取到不匹配的参考答案。
